## Product responsibility and DDD

Quarantine Sandbox Runtime owns reusable sandbox execution, isolation-policy enforcement, resource bounds, lease/readiness/cleanup attestation, hostile-workload execution evidence, application-service isolation, and artifact-analysis evidence. `sandbox_execution` is the Core bounded context; `artifact_analysis` and `application_service` are Supporting contexts. Podman/gVisor/containerd/Kubernetes/VM remain infrastructure adapters. Wardnet retains verdict/incident/quarantine authority. Contextual-Orchestrator and Noema retain Agent/task/tool/application authorization and capability authority. Current structural gaps remain bounded: issue #8 owns the future durable admission/session/recovery separation; persistence has no authority yet and requires a dedicated ADR/3NF/recovery contract before introduction; the repository name remains broader in responsibility than its security-biased name and is a pre-GA product-setting decision rather than a source-layout workaround.

## Artifact analysis

The active foundation keeps SHA-256 artifact identity, bounded ingestion, deterministic format classification/evidence ordering, and analyzer failure attribution under `src/artifact_analysis/`. Draft #18 owns issue #17's Claude-plugin package-analysis contract RED while preserving quarantine-sandbox-runtime as evidence/isolation owner; AppGuardrail remains static-scan/SARIF authority and Noema remains admission/activation authority.

Issue #49 is now a separate P0 artifact-analyzer isolation/evidence RED. Current `AnalysisEngine::analyze_bytes` invokes arbitrary public `StaticAnalyzer` trait objects directly in the runtime host process and then unconditionally publishes policy/runtime evidence that no network access, credential availability, or dynamic execution occurred. That claim is not enforceable against the repository's already-modeled compromised-analyzer adversary. Test-bearing `d67e16a241335b3d3ecd4e37cc80d9efc5200342` attempts a loopback TCP connection from an otherwise-valid static analyzer and requires the runtime host connection not to succeed. The checked-in RED permits either fail-closed rejection before analyzer invocation or an enforceable capability-denying worker, but it forbids treating the in-process trait call itself as an isolation boundary. `docs/doctoring/ARTIFACT_ANALYZER_ISOLATION_TRACEABILITY.md` records the NIST SP 800-190 and Rust process-capability evidence chain.

Issue #50 and Draft #51 separately close the worker-to-controller resource-isolation gap. `StaticAnalyzer::analyze` currently hands the controller an already-materialized `Vec<AnalyzerFinding>`, and the engine accumulates all findings before aggregate validation. Test-bearing `618f3dae4fa7909a8725ab67895375abebba6339` amplifies one small immutable artifact into 512 individually valid findings against issue #17's versioned 65,536-byte output-budget fixture and forbids an over-budget aggregate from becoming `Completed` evidence. The eventual GREEN must enforce versioned byte/count budgets while reading/framing/normalizing worker output, terminate/clean the exact worker on overflow, and never present truncation as completeness. A larger controller heap or post-hoc validation of an attacker-sized vector is not resource isolation.

Issue #52 closes a different evidence-contract contradiction. `AnalysisProfile` already exposes Linux/Windows dynamic profiles and `EvidenceKind` exposes `RuntimeBehavior`, but `RuntimeManifest::validate()` currently rejects every `dynamic_execution_performed=true` manifest regardless of requested profile. Test-bearing `4cc901d7cb40bdc833e08b0c695ba12c27fa2f68` requires truthful completed Linux/Windows dynamic receipts to be representable while preserving `StaticOnly + dynamic_execution_performed=true` as invalid. The smallest causal GREEN is profile-aware, version-compatible manifest/bundle validation; it does not implement the worker or weaken no-network/no-credential policy. `docs/doctoring/ARTIFACT_DYNAMIC_ATTESTATION_TRACEABILITY.md` keeps requested profile, actual execution, exact worker evidence, and consumer verdict authority distinct.

Issue #54 closes the analyzer-provenance identity gap. The public `StaticAnalyzer` contract exposes only `analyzer_id()` plus `analyze()`, while `AnalysisEngine::deterministic_job_id()` hashes only that display identifier rather than the concrete analyzer implementation/version/digest/configuration. Two materially different analyzers can therefore emit different valid evidence under the same deterministic `analysis_job_id` and `producer_id`. Test-bearing `06ee0a1264960843a8ecd93d0e5ecff247866b17` constructs two implementations that deliberately share one analyzer ID but produce different valid `StaticCapability` evidence and requires either deterministic fail-closed admission or distinct provenance-bound job identities. The future GREEN must use stable versioned analyzer artifact/package, semantic-version/configuration and exact-worker provenance; Rust `TypeId`, process addresses/randomness, source paths, or an overloaded runtime `source_revision` are not release provenance. `docs/doctoring/ARTIFACT_ANALYZER_PROVENANCE_TRACEABILITY.md` records the SLSA 1.2/NIST SP 800-218 evidence chain and keeps provenance separate from #49 containment, #50 transport bounds, and #52 execution semantics.

YARA-X/capa/Ghidra/LIEF adapters, dynamic Linux/Windows detonation, durable signed evidence, and immutable analyzer implementation/configuration provenance remain missing commercial slices. New analyzers must execute behind or strengthen the Core sandbox boundary rather than parse hostile artifacts with runtime-host network/environment/filesystem/process authority. Static evidence is not observed runtime behavior, an analyzer worker's no-network/no-credential claims require exact-worker enforcement evidence rather than hard-coded booleans, a dynamic receipt must not understate or fabricate whether execution occurred, and an analyzer display ID must not substitute for executable provenance.
